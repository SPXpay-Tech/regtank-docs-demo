## 30-second smoke test TOKEN=$(curl -sX POST https://crm-server.regtank.com/oauth/token \ -d "grant_type=client_credentials" \ -d "client_id=$ID" \ -d "client_secret=$SECRET" | jq -r .access_token) curl -X POST https://$TENANT-server.regtank.com\ /v2/kyc/exchange/input \ -H "Authorization: Bearer $TOKEN" \ -H "Content-Type: application/json" \ -d '{"surname":"Smith","forename":"John", "referenceId":"user-001"}' # → KYC00121
TL;DR — my recommendation: 🥇 Variant A (Scalar) for the public docs, plus our OpenAPI spec checked into the API repo. Scalar gives us 90 % of Sumsub-tier polish out of the box, free, self-hosted, and re-rendering it just means pushing a new spec.yaml — no second source of truth. The hand-built SPA (Variant E) shows we can absolutely build a Stripe-grade site if we ever need full design control, but that's months of work. Variant A ships today.

What I'd actually ship

Use Variant A (Scalar) as the public docs at docs.regtank.com — point it at spec/regtank-exchange.yaml checked into the API repo. Generate the spec from server-side annotations (springdoc-openapi on the Java side) so docs always match the deployed code. Keep x-codeSamples in YAML files alongside the spec, version-controlled. The hand-built SPA stays in the repo as a reference — it proves we can deliver full design control if the brand team ever decides we need it.
